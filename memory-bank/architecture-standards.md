# Architecture Standards

## System Architecture

- **Modular monolith + SPA + edge gateway**: one Go binary with **thirteen** domain modules composed in `backend/cmd/server.go` and `backend/cmd/worker.go`, plus a `gateway` entrypoint (`backend/cmd/gateway.go`) that boots **no modules** and only proxies. A standalone **Angular SPA** in `frontend/` talks to the API through the gateway. Modules share a process, DB pools, and a contract registry, but communicate only through published interfaces.
- **Role dispatch**: `backend/cmd/root.go:Execute` installs the process logger via `logger.Setup(...)` and then switches on `os.Args[1]` over the five roles (`server`, `worker`, `migrate`, `gateway`, `dlq-replay`). No argument prints usage and exits 2; an unknown role exits 2; a role error is logged with `slog.Error("command failed")` and exits 1.
- **Module boot is four ordered phases** (`backend/pkg/module/module.go`, executed by `backend/cmd/`):
  1. `Init(ctx)` — build each module's internals (repo, service, handlers, relay).
  2. `RegisterContracts(ctx, registry)` — publish each module's contract into `contracts.Contracts`.
  3. `registry.Verify()` (`backend/pkg/module/contracts/contracts.go`) — boot fails if any contract slot is nil.
  4. `RegisterHTTP(ctx, mux)` (server) **or** `RegisterWorkers(ctx, w)` (worker).
  No module may call another before phase 3. `server` runs 4a; `worker` runs 4b; both run 1–3. `gateway` skips all four phases; `migrate` only runs dbmate.
- **Server modules** (`backend/cmd/server.go`), in order: `category`, `catalog`, `customer`, `address`, `auth`, `avatar`, `order`, `payment`, `shipping`, `notification`, `cart`, `wishlist`, `showcase`. `category` must register its contract before `catalog` builds its service; `order` needs catalog/customer; `shipping` needs customer/address; `cart` needs catalog/customer/order/shipping; `wishlist` needs catalog/customer. `showcase` is built with the **read pool only** (no metrics recorder).
- **Worker modules** (`backend/cmd/worker.go`), in order: `category`, `catalog`, `customer`, `address`, `auth`, `order`, `payment`, `shipping`, `notification`. It does **not** boot `avatar`, `cart`, `wishlist`, or `showcase`. Auth is required in the worker to provide the `AccountReader` contract for notification email delivery; `address` is required so `shipping` can resolve quotes and create shipments from `order-paid`; `shipping` runs its relay and `order-paid` consumer only in the worker.
- **Worker background tasks** (`backend/pkg/worker`): `AttachBackground(ctx, fn)` starts a long-running loop that must return on context cancellation. `order`, `payment`, and `shipping` attach their outbox relays; `notification` attaches its delivery relay (claims due deliveries and publishes delivery ids to `notification-email|sms|push`); `payment` and `order` attach their own domain runners (`reconciliation.Runner`, `autocancel.Runner`), which drive `application.Reconciler.RunOnce` and `application.AutoCanceller.RunOnce` through the generic `pkg/background.Runner`. `AttachKafka(ctx, topic, group, handler)` starts `KAFKA_CONSUMER_CONCURRENCY` supervised consumer replicas per subscription (default 1) and restarts each with capped exponential backoff when it stops unexpectedly. `AttachKafkaWithOptions` allows a per-subscription override. An opt-in pause gate (`KAFKA_CONSUMER_PAUSE_ENABLED`) stops reads when the write/read pool saturates; the lag monitor (`KAFKA_CONSUMER_LAG_ENABLED`) samples `minimart_kafka_consumer_lag` for every registered (topic, group).
- **Worker HTTP listener**: the worker serves its own `/metrics`, `/livez`, and `/readyz` on `WORKER_HTTP_ADDR` (default `:8081`). It does not serve the API; only the server does.
- **Frontend shape**: Angular 21 standalone SPA — `frontend/src/app/{core,shared,features}`, lazy `loadComponent` routes, signal-based stores, functional guards/interceptor, and a single `ApiClient` that unwraps the response envelope and maps errors to `ApiError`. Auth uses **encrypted HttpOnly cookies**, not browser storage. `API_BASE_URL` comes from `environments/*.ts` (empty = same-origin); the dev server proxies `/v1` and `/swagger` to `http://localhost:8080` through `frontend/proxy.conf.js`. See `frontend-architecture.md`.
- **Layering per domain**: `domain/` (entities, ports, sentinel errors) ← `application/` (use cases over ports) ← `infrastructure/` (Postgres/Mongo/S3/outbox adapters) and `presentation/` (HTTP, Kafka, cross-domain client). `module.go` selects concrete adapters.
- **Route registration**: each domain's `presentation/http.Handlers.Register` accepts `backend/pkg/routes.Registrar` (a one-method `HandleFunc` interface satisfied by `*http.ServeMux`). The `module.Module.RegisterHTTP(ctx, *http.ServeMux)` interface still takes the concrete mux and passes it through. The indirection lets the cross-module coverage test (`backend/internal/routes/routes_test.go`) register every domain's handlers on a recorder instead of a mux and compare the patterns against `PolicyMap`/public paths.
- **Data flow — HTTP**: browser SPA → **gateway** (`logger → metrics → ratelimit (if Redis) → cors → reverse proxy`) → **server** (`logger → metrics → auth → authz → ratelimit → mux → handler → service → domain/ports → infrastructure`). Responses use `backend/pkg/response.WriteJSON` with `Response{time, success, data, error, meta}`.
- **Data flow — events**: aggregate records events → repository writes the aggregate and shared outbox rows in **one transaction** → `backend/pkg/outbox.Dispatcher` relays to Kafka at-least-once → `presentation/message/event` consumers process under a consumer group. Relays run only in the worker (`w.AttachBackground(ctx, m.relay.Run)`). Shipping now writes its outbox row in the same transaction as the shipment/quote (`publisher.Send(ctx, msg, tx)` with a valid `pgx.Tx`).
- **Integration points**:
  - **Postgres**: primary/replica pools from `backend/cmd/deps.go:newPools`; each SQL domain splits `infrastructure/postgres/reader` and `.../writer` generated by sqlc. Owns catalog, category, customer, address, auth/RBAC, avatar metadata, orders, payments, shipping (methods/zones/rates/quotes/shipments/tracking events), the `product_rating_summary` rating aggregate, and the outbox; `showcase` reads the shared `products` table through the replica only.
  - **Kafka**: topics/groups in `backend/pkg/kafka/topics.go` — **17 source topics** and **12 consumer groups**. Publish paths: `order`, `payment`, `catalog`, and `shipping` publish through their outboxes; the `notification` relay publishes delivery ids directly to the channel topics. Consumers: order consumes `order-placed` (`order-confirmation`) and `payment-succeeded`/`payment-failed`/`payment-unknown` (`order-payment`); catalog consumes `order-stock-release` (`catalog-stock`) and `review-created` (`review-moderation`), and `review-moderated` (`review-rating-aggregator`); notification consumes `order-placed`, `order-cancelled`, `payment-succeeded`, `payment-failed` (`notification`), `shipment-created`, `shipment-shipped`, `shipment-delivered` (`notification-shipment`), and `notification-email`/`notification-sms`/`notification-push` (`notification-email`/`notification-sms`/`notification-push`); shipping consumes `order-paid` (`shipping-shipment-creation`); payment consumes `order-cancelled` (`payment-refund`) to refund captured payments of cancelled orders. `payment-initiated` and `payment-refunded` have no consumer.
  - **MongoDB**: `notification` records (`notifications`, unique `dedupe_key`, plus `notification_deliveries`, unique `(notification_id, channel)`) and preferences (`notification_preferences`, `_id = user_id`); `cart` documents (`carts`, unique partial index on `customer_id` where live, plus `version` optimistic locking); `wishlist` documents (`wishlists`, unique by `customer_id`).
  - **Redis**: `pkg/idempotency`, `pkg/ratelimit`, `pkg/authz.CachedStore`, the catalog review/rating read cache, and the gateway limiter — accelerators only, all fail open. Each adapter namespaces its keys (`idempotency:`, `ratelimit:`, `rbac:perm:`, `catalog:reviews:`, `catalog:rating:`) so the shared instance cannot cross-contaminate. Redis is not pinged at boot; `/readyz` reports it as a non-critical dependency (`degraded` with HTTP 200 when unavailable by default). The shipping module uses its `idempotency.Store` and `SHIPPING_IDEMPOTENCY_TTL` (24h) for both quote creation (keyed `shipping:quote:<client key>`) and shipment creation from `order-paid` (keyed `shipping:shipment:<order id>`); the DB unique indexes (`shipping_quotes.idempotency_key`, `shipments.order_id`) are the authoritative fallback.
  - **Moderation**: `backend/pkg/moderation` defines the provider port; `llamaguard` calls an Ollama-hosted Llama Guard 3 model over HTTP. Catalog builds the Llama Guard client when `conf.ModerationEnabled()` (default true) and otherwise falls back to `moderation.NewNoopProvider()`, which approves everything with model `noop`. A runtime provider error aborts moderation and leaves the review `pending`. Ollama runs under docker-compose `--profile moderation`.
  - **S3-compatible storage**: `backend/pkg/storage/s3.Client` wraps AWS SDK v2 with two clients — an internal one for uploads/deletes and a presign one pointing at `S3_PUBLIC_ENDPOINT` (falling back to `S3_ENDPOINT`) for browser-facing URLs. Catalog product images (`product_images`, many per product, ordered by `position`) and avatars use it; uploads are size/type bounded.
  - **Gateway**: `backend/cmd/gateway.go` serves local health/metrics and proxies the rest via `httputil.ReverseProxy`, rewriting URL/Host and forwarding `X-Forwarded-*`. CORS is applied to all responses; `OPTIONS` short-circuits with 204. Optional Redis rate limiting keyed by `Idempotency-Key` (falls back to client IP). No Postgres/Mongo/Kafka dependency. Depends on Redis for optional rate limiting.
  - **Frontend**: consumes `showcase`, `category`, `catalog`, `auth`, `address`, `avatar`, `cart`, `wishlist`, `customer`, `order`, `payment`, `shipping`, and `notification` endpoints. Cookies are sent automatically (`withCredentials` semantics); cart and wishlist are authenticated and scoped to the cookie's user. Shipping quote creation, methods, and shipment reads are authenticated; cart checkout forwards `shipping_quote_id` and `address_id`.
  - Payment provider: `backend/internal/payment/domain/provider.go` (`Authorize`/`Capture`/`GetStatus`/`Refund`), sole adapter `infrastructure/provider/fake`.
  - Email: `backend/internal/notification/infrastructure/email/resend` sends via Resend (`RESEND_API_KEY`, `RESEND_FROM`, `RESEND_REPLY_TO`); `cmd/deps.go:newEmailSender` falls back to `.../email/log` when the key is unset.
- **Cross-domain calls**: only through `contracts.Modules` (`backend/pkg/module/contracts`), implemented by `presentation/module/` adapters and published in `RegisterContracts`. **Seven domains publish contracts: `address`, `auth`, `catalog`, `category`, `customer`, `order`, `shipping`.** Consumers: `address` → customer; `auth` → customer (signup provisioning); `cart` → catalog + customer + order + shipping; `catalog` → category + customer (review submission); `notification` → auth + customer + address (recipient email and phone); `order` → catalog + customer; `payment` → order (pre-charge order validation and refund checks); `shipping` → address + customer; `wishlist` → catalog + customer. `avatar`, `cart`, `notification`, `payment`, `showcase`, and `wishlist` publish none. `contracts.Modules` embeds six slots (catalog, category, customer, order, shipping, address); the concrete `contracts.Contracts` struct adds `AuthClient` for seven total, and `Verify()` fails boot if any is nil.
- **Auth (encrypted cookie JWT + RBAC)**: `backend/pkg/auth` issues HS256 JWTs and encrypts them with AES-GCM into `mm_at`/`mm_rt` cookies. `CookieConfig` sets `HttpOnly`, `SameSite=Lax`, path `/`, and `Secure` in production. Access TTL defaults to 15m; refresh TTL 7d, or 30d for `remember_me`. `backend/pkg/authz` adds the permission policy/cache; authz is fail-closed.
- **Route-pattern resolution**:
  - The authz middleware is mounted **outside** the `ServeMux`, so `r.Pattern` is empty when it runs. It resolves the route through `authz.Router` — `*http.ServeMux.Handler(r)` — and uses the **registered** pattern (`GET /v1/products/{id}`), not the concrete path.
  - `Route.Pattern` is method-qualified and keys `PolicyMap`; `Route.Path` is path-only and keys `PublicPaths`/`OptionalAuthPaths`.
  - Placeholder keys in public/optional maps match concrete segments because the compared value is the pattern path.
  - Unknown routes fall back to the concrete URL path and remain fail-closed.
  - `auth.PublicPaths` matches exact paths and trailing-slash prefixes (`/v1/showcase/products/`); `/swagger/` is always public. Cart, wishlist, and shipping routes are protected.
  - Public routes are defined centrally in `backend/pkg/auth/paths.go:PublicRoutePaths` and shared with `authz.PublicPaths` so they cannot drift.
- **Showcase (public read-only)**: replica-only reader over `products`; no writes, Kafka, or contract. Supports pagination and `category_id` filtering.
- **Cart (MongoDB, HTTP-only)**: consumes catalog/customer/order contracts, publishes nothing, and runs only in the server role.
- **Category**: CRUD over `categories`, publishes `GetCategory`, and validates the category on catalog product writes. Name is unique case-insensitively.
- **Address**: authenticated CRUD; resolves the caller's customer through `customer.EnsureCustomer(userID)` and checks ownership on every operation. Default address is unique per customer.
- **Avatar**: authenticated self-upload, metadata in Postgres, binary in S3, presigned URL on read. `avatars:read` permits reading another account's avatar; `avatars:write` plus the path/claim equality check protects writes.
- **Shipping (Postgres, HTTP + worker)**: admin CRUD for methods/zones/rates, customer-facing quote creation and shipment reads, fulfillment transitions (`process` → `dispatch` → `deliver`), and tracking events. Publishes `ShippingClient`; consumes `order-paid` to create one shipment per order. Quotes snapshot the destination and cost, expire, and are idempotent by their `Idempotency-Key`; shipments are idempotent by `order_id`.
- **Review moderation (catalog)**: `AddReview` writes the review as `pending` and a `review-created` outbox row in the same transaction. The catalog worker consumes it, calls the moderation provider, and transitions the review to `approved`, `rejected`, or `needs_review`, updating product rating counters on approval and writing a second `review-moderated` outbox row in the same transaction. A separate catalog consumer group (`review-rating-aggregator`) consumes `review-moderated` and recomputes the product's rating aggregate (`products.total_rating`/`total_reviews` plus the `product_rating_summary` row) idempotently from the approved reviews. With moderation disabled the noop provider approves everything; if the provider errors (e.g. Ollama unreachable) the review stays `pending` and the message is retried/dead-lettered.
- **Health**: `backend/pkg/health.Handler` serves `/livez` (always 200 `{"status":"alive"}`) and `/readyz` (pings every dependency with a 2s timeout). A dependency is `Critical` (down ⇒ 503, body status `unhealthy`) or non-critical (down ⇒ 200, body status `degraded`). The body is `{time, status, checks: {<name>: {status, latency?, error?}}}`. The server and worker check Postgres read/write, Mongo, and Redis (Redis critical only when `REDIS_REQUIRED_FOR_READINESS=true`); Kafka and S3 are not probed; the gateway is dependency-free.

## Design Patterns

- **Ports & adapters everywhere**: services depend on interfaces (`domain.Repository`, `contracts.Modules`, `idempotency.Store`, `metrics.Metrics`, `kafka.Publisher`, `worker.Subscriber`, `health.Pinger`, `authz.PermissionStore`, S3 client). Compile-time proofs: `var _ module.Module = (*Module)(nil)`, `var _ domain.Repository = (*Repository)(nil)`.
- **Edge reverse proxy**: the gateway is a thin `http.Handler` around `httputil.ReverseProxy`; configuration is `GATEWAY_*`; the proxy package is dependency-free and unit-tested.
- **CORS**: `backend/pkg/cors.Middleware(Config)` supports allow-lists or `*`, reflects origin when credentials are enabled, emits preflight headers, and answers `OPTIONS` with 204. Wired only in the gateway.
- **Encrypted-cookie auth**: login sets `mm_at` and `mm_rt`; refresh reads/decrypts `mm_rt`, validates it, and performs sliding renewal of both cookies; logout is public and clears both. The SPA never receives tokens in JSON and cannot read the cookies from JavaScript. The HttpClient layer must send cookies (same-origin or credentialed CORS).
- **Transactional outbox** (order, payment, catalog, shipping): `outbox.Publisher.Send(ctx, msg, tx)` inside `Save`/`Update`; core in `backend/pkg/outbox/`; Postgres adapter in `backend/pkg/outbox/postgres`; Kafka adapter in `backend/pkg/kafka/outbox_broker.go`. Order, payment, catalog, and shipping write the outbox row in the same transaction as the aggregate change. Consumers must be idempotent.
- **Outbox dispatcher**: `outbox.Dispatcher` runs three independent loops (`backend/pkg/outbox/dispatcher.go`) — `record-processor` (poll + publish pending records), `record-unlocker` (reclaim locks older than `MaxLockTimeDuration`), and `record-cleaner` (remove records older than `MessagesRetentionDuration`). Each loop runs once immediately and then on its own ticker; a failed iteration is logged and retried on the next tick. Every dispatcher instance locks records under its own lock id (`<machine-id>/<random>`), so the per-domain dispatchers that share the worker host never publish each other's records.
- **Notification delivery**: `notification` consumers ingest an event into one `notifications` row plus one `notification_deliveries` row per eligible channel, and the notification relay (`backend/internal/notification/infrastructure/relay`) claims due deliveries and publishes the delivery id to `notification-email`, `notification-sms` or `notification-push`. The channel consumer renders the template, resolves the contact, calls the provider, and retries transient failures with backoff before dead-lettering.
- **Retry and dead-letter topic**: handlers retry in-process with exponential backoff and jitter; permanent errors skip retries. Exhausted or permanent failures are republished to `<topic>.dlq` with `x-minimart-*` triage headers, and only then is the original acknowledged. A DLQ publish failure leaves the original unacked for redelivery. The operator replays with the `dlq-replay` role (`make -C backend dlq-replay topic=...`); nothing consumes DLQs automatically, and a message is parked once it reaches `--max-replays` (default 3). The worker restarts a consumer loop that stops unexpectedly, with capped backoff.
- **Idempotency — Lookup → Reserve → Process → Complete (+ Release)**: Redis cache in front, DB unique index authoritative (`orders.idempotency_key`, `payments.idempotency_key`, `shipping_quotes.idempotency_key`), fingerprint = length-prefixed SHA256, in-flight TTL 1m, completed TTL 24h. The generic `idempotency.Coordinator[T]` (`backend/pkg/idempotency/coordinator.go`) owns the flow — `Existing` (replay vs conflict vs in-progress), `Reserve`, `Complete`, `Release` — and **fails open** on store errors: a reserve error proceeds, a get error falls back to the DB lookup, and complete/release errors are logged but not fatal. The shipping module is constructed with an `idempotency.Store` and `SHIPPING_IDEMPOTENCY_TTL` (24h): quote creation remembers its key under `shipping:quote:<client key>` (fingerprint: customer, method, address, subtotal) and shipment creation under `shipping:shipment:<order id>` (fingerprint: the `order-paid` payload). Both also fall back to DB lookups (`GetQuoteByIdempotencyKey`, `GetShipmentByOrderID`). Conflict and in-progress errors are domain/application sentinels.
- **Circuit breaker around Redis**: `backend/pkg/resilience.Breaker` is an in-process breaker (`FailureThreshold`, `OpenDuration`, `HalfOpenMax`, `SuccessThreshold`) wrapping the Redis-backed idempotency store and rate limiter (`pkg/idempotency/resilient`, `pkg/ratelimit/resilient`). Each call also gets a short timeout (default 200ms). The breaker returning `ErrOpen` is treated like any other store error, so both paths stay fail-open.
- **Valid by construction**: entities exist via `New<Entity>(...)` constructors (`NewOrder`, `NewProduct`, `NewCategory`, `NewAddress`, `NewAvatar`, `NewPayment`, `NewAccount`, `NewCustomer`, `NewCart`); no public setters.
- **Idempotent state transitions**: `Order.MarkPaid`/`MarkPaymentFailed`/`MarkPaymentUnknown` and cart transitions are no-ops when already in the target/invalid state and record no event. Terminal/absorbing states are documented on methods.
- **Cart state machine**: `active` → `checkout_pending` → `consumed`; `consumed` is terminal. `BeginCheckout(key)`, `MarkConsumed(orderID)`, and `ReleaseCheckout()` own transitions; item mutations require `active`.
- **Optimistic locking on MongoDB** (cart): `Update(ctx, cart, expectedVersion)` filters on `(_id, version)` and sets `version = expectedVersion + 1`; zero matches triggers a probe to distinguish not-found (404) from stale version (409).
- **Compare-and-set persistence**: order updates use `WHERE id=$1 AND status=$2`; a stale expectation yields `ErrOrderStateChanged` (benign in `ApplyPaymentOutcome`) or `ErrOrderNotFound`.
- **Optimistic locking in SQL** (catalog, customer, category, address): entities carry `Version int` starting at 1. Checked writes require the caller's version (body and/or `If-Match`; header wins). CAS uses `WHERE id=$1 AND version=$n RETURNING ...`; 0 rows probes the write pool to distinguish 409 `Err<Entity>OptimisticLock` from 404 not-found. System writes (stock reserve/restore, customer deactivate) bump version unconditionally. Responses expose `ETag: "<version>"`; GET supports `If-None-Match` → 304. Category/address delete also require a positive version.
- **RBAC**: roles/permissions are data seeded by migrations; `PolicyMap` maps route patterns to permissions; `authz.Middleware` extracts claims, loads permissions via `PermissionStore`, and returns 403 on mismatch. Fail-closed for missing policy; cache fail-open on Redis errors.
- **Two-level permission cache**: `authz.CachedStore` (`backend/pkg/authz/cache.go`) keeps an in-process L1 map guarded by an RWMutex (`RBAC_PERMISSIONS_LOCAL_CACHE_TTL`, default 1m) in front of a Redis L2 entry (`rbac:perm:<account_id>`, `RBAC_PERMISSIONS_CACHE_TTL`, default 5m), which sits in front of the Postgres store. A `singleflight.Group` collapses concurrent misses for the same account into one DB query.
- **Shared country normalization**: `backend/pkg/country.Normalize` maps known localized names (`brasil`, `brazil`, `brasil.`) to their ISO-3166 alpha-2 code and upper-cases any two-letter value; anything else is returned trimmed and unchanged. `country.Equal` compares two values after normalization. Used by the address domain (on create/update) and the shipping zone matcher.
- **Shared S3 client**: `backend/pkg/storage/s3.Client` holds an internal `*s3.Client` for uploads/deletes and a second presign client pointed at `S3_PUBLIC_ENDPOINT`, so browser-facing URLs can use a different host than the server. `Upload`, `Delete`, `PresignGet`, and `Bucket` are the whole surface; catalog, avatar, and showcase share it.
- **Cross-domain checkout saga**: cart calls `order.PlaceOrder` synchronously, bracketting it with `BeginCheckout`/`MarkConsumed`; business failures release the cart, technical failures leave it `checkout_pending`, and retries reuse the same idempotency key so order idempotency collapses them to one order.

## Technical Decisions

- **Modular monolith over microservices**: shared transaction boundary for aggregate + outbox, one deployable, contracts instead of network calls. Trade-off: no independent scaling; mitigated by server/worker role split.
- **One binary, five roles**: identical modules boot in server and worker, differing only in phase 4; gateway, migrate, and the operator-only `dlq-replay` are additional entrypoints. Trade-off: worker builds HTTP objects it never registers.
- **Outbox over dual-write/2PC**: at-least-once delivery and consumer idempotency instead of a distributed transaction.
- **Postgres reader/writer split**: explicit read scale without an ORM; sqlc with migrations as schema source; generated files are never hand-edited.
- **Redis as accelerator only**: correctness never depends on it; an extra DB lookup on cache miss/failure is accepted.
- **stdlib HTTP + plain switch**: no framework/cobra; explicit routing and `os.Args` dispatch.
- **Edge gateway separate from the app**: CORS and edge rate limiting live outside the server; authorization deliberately stays in the app. Trade-off: an extra hop and a second rate-limit window when both use Redis.
- **Angular SPA with encrypted HttpOnly cookies**: tokens are not stored in `localStorage`; the browser sends them automatically, protecting against XSS token theft. Trade-offs: the API and SPA must be same-site/credential-compatible; cookies use `SameSite=Lax` but there is no separate CSRF token.
- **Environment-only config with local defaults**: runs with no `.env` in dev; production supplies env vars.
- **Fake payment provider with env-tunable decline/timeout amounts**: failure paths are testable end-to-end; timeouts map to `unknown`, never `failed`.
- **Docs generated and excluded from lint**: served only outside production.
- **Auth as a domain module**: owns accounts, passwords, JWTs, cookies, and RBAC data; publishes `AuthClient` (used by notification to resolve recipient emails) and boots in both server and worker.
- **Permission cache in Redis with TTL** (`RBAC_PERMISSIONS_CACHE_TTL`, default 5m): avoids a DB round-trip; cache errors fall back to DB.
- **Order contract for cart checkout**: `PlaceOrder` with transport-neutral sentinels avoids an async command/reconciliation loop and reuses order idempotency.
- **Cart in MongoDB**: a cart is a single mutable document; uniqueness and optimistic locking are Mongo index/query guarantees.
- **Cart endpoints authenticated**: `/v1/cart` requires `cart:read`/`cart:write`; identity comes from the access-token cookie and the cart is scoped to that user.
- **Category as a published contract**: catalog validates product categories in-process without reading category tables; deletion is blocked by FK/domain rules rather than cross-domain SQL.
- **Category endpoints are protected**: `/v1/categories` is no longer public; `GET` requires `catalog:read` and `POST` requires `catalog:write`. Public category browsing is available via `GET /v1/showcase/categories`.
- **Address uses the customer contract**: handlers derive the user from the access cookie and call `EnsureCustomer(userID)`, so client-supplied customer ids are never trusted.
- **Avatar metadata in Postgres, bytes in S3**: presigned URLs avoid proxying image bytes; uploads are self-only and browser-facing URLs use `S3_PUBLIC_ENDPOINT`.
- **PGO**: `default.pgo` is picked up automatically when present; CI generates it only on main and uploads a PGO binary.
- **Worker HTTP listener**: the worker serves `/metrics`, `/livez`, `/readyz` on its own address (`WORKER_HTTP_ADDR`, default `:8081`) for independent observability.
- **Route registration via Registrar**: modules depend on `backend/pkg/routes.Registrar` instead of `*http.ServeMux`, enabling the cross-module policy-coverage test to verify every route has an authz policy.
- **Shared logger package**: `backend/pkg/logger` owns slog setup, the request-scoped logger, and the `X-Request-ID` correlation header. Every role installs it before doing work, so server, worker, and gateway emit the same structured shape.
- **Redis breaker over Redis retries**: `backend/pkg/resilience` adds an in-process circuit breaker in front of Redis so a Redis outage stops hammering the socket instead of adding latency to every request. Correctness is unaffected because Redis is already an accelerator.
- **One S3 client package**: `backend/pkg/storage/s3` removes three copies of S3 wiring (catalog, avatar, showcase) and makes the internal-vs-presign endpoint split explicit.

## Implementation Guidelines

- **Critical paths**:
  - **Order placement**: idempotency → `GetProduct` per item → `EnsureCustomer` → `NewOrder` → `ReserveStock` (all-or-nothing, keyed by order id) → `Save` (order + items + outbox in one tx) → release stock best-effort if save fails.
  - **Payment outcome → order**: `payment-outcome` consumer → `ApplyPaymentOutcome` → CAS update; lost races are no-ops.
  - **Refund on cancelled order**: a captured payment for a cancelled order is reversed to `refunded` three ways — inline (CreatePayment re-checks the order after capture and refunds immediately, keeping the charge reference on the payment if the refund fails so the reconciler retries), the `order-cancelled` consumer (`payment-refund` group, `RefundOrderPayments`, idempotent and tolerant of lost races), and the reconciler (a captured charge confirmed on a cancelled order is refunded, not finalized). `POST /v1/payments/{id}/refund` refunds a `succeeded` payment manually, but only when its order is `cancelled`; already-refunded is a replay. Refunds publish `payment-refunded` (no consumer).
  - **Stock release**: `order-stock-release` → catalog `ReleaseStock`, idempotent through the reservations ledger.
  - **Signup**: `NewAccount` (bcrypt hash) → save → `EnsureCustomer(account.ID)` → assign default `customer` role. **Login**: verify password → issue access/refresh JWT → encrypt into cookies → return user info plus access expiry. **Refresh**: decrypt `mm_rt` → validate → sliding renewal of both cookies → return new access expiry. **Logout**: public; clear both cookies. **Change password**: self only, requires current password and matching confirmation.
  - **Admin seeding**: `ADMIN_USERNAMES` → `EnsureAdmins` → idempotent `AssignRole(..., "admin")`.
  - **Authz**: auth resolves claims → authz resolves pattern, checks policy, loads cached permissions → 403 if missing. Permission-lookup errors return 500 (Redis fails open; DB failure reaches this branch).
  - **Address**: cookie user → `EnsureCustomer` → pass `cust.ID` into application use cases; every get/update/delete/set-default checks `address.CustomerID == cust.ID` and hides mismatches as not-found.
  - **Category on product write**: catalog calls `registry.Category.GetCategory` before create/update; `ErrCategoryNotFound` maps to 400.
  - **Avatar upload**: cookie user must equal `{account_id}`, multipart image validation (type, size), S3 upload, metadata upsert, presigned URL.
  - **Payment reconciliation** (worker only): every `PAYMENT_RECONCILE_INTERVAL` (1m) the reconciler lists `pending`/`unknown` payments older than `PAYMENT_RECONCILE_AGE` (5m, capped at `PAYMENT_RECONCILE_BATCH_SIZE`, 100), asks the provider for `GetStatus(providerRef)`, applies the outcome with `Payment.ApplyReconciliation`, and persists it with `repo.Reconcile`. A payment with no `provider_ref` is skipped; a provider error, a non-pending payment, or a failed write is logged and skipped without stopping the loop. When the provider confirms a captured charge whose order was cancelled (the order can be cancelled while a payment is `unknown` because `Order.Cancel` only rejects `cancelled`/`paid`), the reconciler refunds it instead of finalizing it, so the succeeded state is never visible; a lost refund race (`ErrPaymentNotRefundable`) is benign and left to the next pass.
  - **Rating aggregation** (catalog worker): `review-moderated` → `AggregateRating` → `Service.UpdateRatingSummary` recomputes the sum/count from the approved reviews and writes both `products.total_rating`/`total_reviews` and the `product_rating_summary` row. It is idempotent and safe to replay; a missing product is a `kafka.Permanent` error.
  - **Cart checkout**: validate `user_id` + `Idempotency-Key` + `shipping_quote_id` + `address_id` → `EnsureCustomer` → `GetQuote` + ownership check + `ValidateQuote` → load cart → `BeginCheckout` + CAS update → re-read → `PlaceOrder(userID, quote snapshot, ...)` → `MarkConsumed` + CAS update. Business failure releases; technical failure leaves `checkout_pending`; `MarkConsumed` failure still returns the existing order. `address_id` is required but is not separately re-validated by cart; the quote already snapshots the destination.
  - **Shipping**: quote creation resolves the caller's customer → validates method active → `GetAddress` via the address contract (ownership) → matches zone by destination → picks an active rate → snapshots destination/cost with an expiry. It is idempotent by the required `Idempotency-Key` (Redis + unique `shipping_quotes.idempotency_key`); a replay returns the original quote and a key reused with different customer/method/address/subtotal is 409. `order-paid` → `CreateShipmentFromOrderPaid` is idempotent by `order_id` (Redis `shipping:shipment:<order_id>` + unique `shipments.order_id`), returns the existing shipment if one exists, validates quote ownership/status, creates the shipment, consumes the quote, and publishes `shipment-created` in the same transaction.
  - **Gateway**: build recorder → optional Redis (skip limiter on error) → proxy → local health/metrics → CORS → optional limiter → metrics/logging middleware. Graceful shutdown on SIGINT/SIGTERM.
  - **Frontend auth**: `provideAppInitializer()` awaits `AuthService.initAuth()` → `/v1/auth/me` with cookies; unauthenticated is a normal state. Login/register refresh the user; a `401` triggers one `/v1/auth/refresh` retry. The refresh service clears local state only on `401`/`403`, and `AuthService` proactively refreshes from the returned expiry with retry/backoff. No token storage service.
  - **Frontend checkout**: cart/user ids and idempotency keys come from stores/services; navigates to order details on success. `ApiClient` now supports custom headers; `CartService.checkout` and `PaymentsApiService.create` forward the `Idempotency-Key`. Payment creation is followed by status polling.
- **Rules that must not be broken**:
  - Never import another module's `application/` or `infrastructure/` — only `presentation/module/client` + `contracts.Contracts`.
  - Never hand-edit sqlc-generated files; run `make -C backend sqlc`.
  - Never write another domain's tables directly.
  - Modules communicate in-process through contracts; Kafka is the async path.
  - Keep `ctx` first and never store it in a struct.
  - Outbox relays and Kafka consumers only in `RegisterWorkers` (worker role).
  - Do not move auth/authz into the gateway.
  - Every user-facing event needs a notification counterpart.
  - Adding a route requires a `PolicyMap` entry; public routes need entries in **both** `authz.PublicPaths` and the `auth.PublicPaths` list.
  - RBAC changes require a new migration.
  - The contracts registry is the cross-domain allow-list: `catalog.CatalogClient`, `category.CategoryClient`, `customer.CustomerClient`, `order.OrderClient`, `shipping.ShippingClient`, `address.AddressClient`, and `auth.AuthClient`; `Verify()` fails if any is nil.
  - Every HTTP route needs a `PolicyMap` entry. Public routes must appear in both `auth.PublicPaths` and `authz.PublicPaths`; `/v1/shipping/*` is protected, so shipping reads require an authenticated user with `shipping:read`.
- **Common pitfalls**:
  - Publishing directly from application code instead of the repository/outbox transaction.
  - Treating Redis as authoritative.
  - Assuming at-least-once consumers never see duplicates.
  - Assuming failed Kafka handlers are retried by the broker. The consumer retries in-process, then dead-letters with triage headers and acks; only shutdown leaves a message unacked for redelivery.
  - Cancelling a paid order or resurrecting a terminal order with a late event.
  - Forgetting `Idempotency-Key` on `POST /v1/orders`, `POST /v1/payments`, `POST /v1/cart/checkout`, or `POST /v1/shipping/quotes`.
  - Forgetting a `PolicyMap` entry — the route returns 403 (fail-closed). `internal/routes` registers every module's routes on a recorder and fails the build when a route is neither public nor governed by a policy.
  - Assuming an order placed without shipping later gains shipping data. The `orders` table stores the shipping snapshot (`shipping_quote_id`, `shipping_method_id`, `shipping_method_name`, `shipping_cost_cents`, `destination_snapshot`); it is written with the order and returned by `GetOrder`/`GetByID`/list reads, by the order contract, and in the order HTTP response.
  - Assuming `/v1/categories` is public — it now requires authentication and `catalog:read`/`catalog:write`. Use `/v1/showcase/categories` for unauthenticated browsing.
  - Assuming cart state survives reload — it is re-fetched; only UI state is in memory.
  - Assuming SPA auth state survives reload — `initAuth()` must complete before protected data is requested.
  - Forgetting the frontend dev proxy (`/v1` → `http://localhost:8080`).
  - Treating `country.Normalize` as a strict ISO-3166 validator — it only maps known aliases and upper-cases two-letter values; anything else passes through unchanged.
  - Assuming the rating summary is exposed over HTTP — `GetReviewSummary`/`GetRatingSummary` are application use cases with **no** HTTP route; the SPA computes the displayed average from the loaded review page.
- **Security considerations**:
  - `gosec`, `noctx`, bounded `ReadHeaderTimeout`, and global token-bucket rate limiting (`Idempotency-Key` with client-IP fallback, 429 + `Retry-After`) in both gateway and server.
  - Swagger hidden in production; `/readyz` pings dependencies with a 2s timeout; gateway readiness is dependency-free.
  - Secrets come from env/CI only. `govulncheck` runs in CI.
  - Passwords are bcrypt-hashed and never logged.
  - JWTs are HS256 (`JWT_SECRET`); cookie payloads are AES-GCM encrypted with `COOKIE_ENCRYPTION_KEY` (32 bytes).
  - Auth cookies are `HttpOnly`, `SameSite=Lax`, and `Secure` in production. There is no separate CSRF token; cross-site state-changing requests are mitigated by `SameSite=Lax` and CORS policy.
  - Authorization is fail-closed; unknown routes deny by default.
  - The cart tree is authenticated and scoped to the caller — anything under `/v1/cart` inherits that posture.
  - `/v1/categories` requires `catalog:read` (GET) / `catalog:write` (POST, PATCH, DELETE). Public browsing uses `/v1/showcase/categories`.
  - Product review routes are governed: `POST /v1/products/{id}/reviews` requires `reviews:write` (held by `customer` and `admin`), `GET /v1/products/{id}/reviews` requires `catalog:read`. A submitted review is attributed to the customer resolved from the session, so a caller cannot post on behalf of another customer. The public showcase reviews endpoint remains the customer-facing read path.
  - Avatar reads require `avatars:read` but are not self-only; avatar writes require `avatars:write` **and** a path/claim match.
  - The gateway is not an authorization boundary — it validates/strips nothing; the server always enforces auth/RBAC.
  - CORS defaults to `GATEWAY_CORS_ORIGINS=*` with credentials enabled; production should use explicit origins.
  - `X-Request-ID` is honored when supplied by a client and echoed on the response; treat it as a correlation hint, not an identity claim.
